위 유형을 지원할 수 있는 공통 계약을 설계하되, 모든 유형의 AI 구현이 확정되었다고 간주하지 않는다. Mapping 추천은 확인된 적용 범위이며, Target 설계 세부 범위와 신규 도메인·코드 생성 방식은 검토 항목이다. DQ 규칙 추천, 엔터티 통합 규칙 자동 생성, 음성/STT, 특정 논문·온톨로지 도입은 이번 계약으로 기능을 확정하지 않는다.

표준화는 업무 개념과 표현을 정하는 일이고, Target 설계는 테이블 구조를 정하는 일이다. Mapping은 원천을 승인된 구조에 대응시키는 일이며, 실제 이관은 별도 실행 단계다. 하나의 추천 요청으로 이 네 가지를 암묵적으로 완료 처리하지 않는다.

1.3 하드코딩하지 않을 항목

특정 고객사·원천 시스템 수, 테이블 목록, Lakehouse 이름, 저장 경로, API 주소, 모델명, 후보 수, 샘플 수, 평가 가중치와 승인 점수 경계를 코드나 공통 계약에 고정하지 않는다. 승인된 정책·설정의 식별자와 버전으로 참조한다. 실제 테이블과의 연결은 어댑터에서 처리하고, 단순 사전 조회·자료형 검사로 충분한 작업은 규칙 방식으로 수행할 수 있다.

원천 항목은 최소한 접근 범위 + 원천 시스템 + 원천 테이블 + 원천 컬럼으로 구분하고, 실행·비교 시 배치와 스키마 버전을 함께 사용한다. 원천에 안정적인 컬럼 ID가 있으면 이름과 함께 보존한다. 여러 원천을 통합할 때도 각 원천의 범위와 식별정보를 유지하며, 범위를 넘는 조회·조합은 별도 권한이 있어야 한다.

코드 대응 키에는 원천 컬럼 식별정보뿐 아니라 코드그룹과 원천 코드값을 포함한다. Target 항목은 적용 범위 + Target 모델 버전 + 테이블·컬럼 식별자로 구분한다. 단어·용어·도메인·코드 사전의 ID도 사전 범위와 버전을 함께 참조한다.

현재 source_table의 논리 명칭과 저장소 컬럼의 대응은 2.4절에 따른다. 응답만으로도 평가 키를 복원할 수 있도록 subject_refs가 참조하는 대상 목록 또는 접근 가능한 불변 대상 명세를 함께 제공한다. 대상 목록에는 범위·시스템·논리 테이블·컬럼·배치·스키마 버전이 포함되어야 한다.

날짜만으로 입력 전체를 식별하지 않는다. 기존 연계에서 source_batch_id가 ingest_date와 같더라도, 계약상 날짜와 배치·실행의 의미를 분리한다. 요청 시각(requested_at), 실행 시작·종료 시각(started_at·completed_at)은 실제 발생한 경우 시간대가 포함된 형식으로 전달한다. 미시작·미종료는 null과 상태로 구분한다. ingest_date 같은 업무 날짜를 시각으로 임의 변환하지 않는다. 같은 날짜의 복수 배치·동시 실행 지원은 별도 합의 사항이며, 식별자를 분리했다는 이유만으로 현재 지원된다고 보지 않는다(QA-016·QA-017).

물리적으로 데이터를 모두 본문에 넣을 필요는 없다. 권한 검사를 거치는 불변 참조를 사용할 수 있다. 입력 스냅샷은 변경 가능한 테이블 경로만 가리켜서는 안 되며, 저장소 버전·읽은 시점의 보존본 또는 내용을 검증할 수 있는 식별정보를 갖춰야 한다.

조건부 필수 항목은 추천 유형에 따라 적용한다. Mapping 요청에는 승인 Target 모델 참조가 필요하고, 코드값 대응에는 원천 코드그룹·값·의미 근거가 필요하다. Target 설계 요청에는 설계 목적과 원천 집합, 사용할 표준의 상태가 필요하다. 조건부 근거가 빠진 항목은 보류할 수 있지만, 요청 식별자·접근 범위·입력 스냅샷 같은 계약 필수값의 누락은 입력 오류로 구분한다.

자료형은 세 가지를 구분한다. 원천이 선언한 타입, 현재 저장소에 보관된 타입, 값과 형식에서 추론한 타입이다. 현재 Bronze·Silver 원천 컬럼이 문자열로 저장된다는 사실만으로 날짜·금액·식별자의 업무 도메인을 문자열로 확정하지 않는다. 원천 선언은 03.1.3의 수집 메타데이터를 우선 공급원으로 연결하되, 해당 자료형이 실제로 제공·검증된 경우만 사용한다. QA-014의 메타데이터 등록 연계는 보완 경로이며 구현 완료로 간주하지 않는다. 원천 선언이 없으면 unknown으로 기록하고, 추론 근거와 변환 실패 가능성을 남긴다. QA-008의 현행 파이프라인 처리 방식 유지 결정도 보존한다.

Mapping의 disposition은 적용 제안(apply_candidate), 제외 제안(exclude_candidate), 보류(hold)처럼 업무 판단을 표현한다. Mapping이라는 결과 유형은 recommendation_type에 둔다. 제외 제안이면 ai_migration_apply=false와 ai_exclude_reason을 기록하고, 기존 분류에 대응할 때 EXCLUDE·NONE을 참고한다. 근거 부족은 제외 확정이 아니므로 적용값을 false로 채우지 않는다.

확인한 제공 코드에서는 원본 정의를 그대로 실행하는 경로 대신 승인 규칙(approved_rule)을 읽고 rule_status=ACTIVE를 선택한다. 내부 어댑터가 이를 REVIEW_STATUS라는 이름으로 바꾸더라도 ACTIVE는 사람의 APPROVED와 다른 상태다. 일부 실행 규칙 구조에는 FINAL_MIGRATION_APPLY_YN이 없으므로 최종 적용·승인·호환성 검사는 06.5.2·06.5.3·07.7.4에 연결한 승인 규칙 발행 단계에서 보장되어야 하며 구현 검증이 필요하다. 제외 승인·보류·미검토 결과를 활성 실행 규칙으로 발행하지 않는다.

기존 정의의 TRANSFORMATION_RULE 문구가 해당 엔진에서 그대로 실행된다는 보장도 없다. 유형·실행 방식·지원 규칙 참조를 확인하고 실행 가능한 형태로 검증한 뒤 발행한다. 제공 초기 적재 코드는 대상 테이블을 전체 교체하므로 검토·승인 행 보존은 별도 확인이 필요하다. Fabric 전환본의 규칙 구조·적재 동작 일치 여부는 02.3.3의 G1 확인 항목으로 남긴다.

모르는 속성은 null과 누락 사유로 표현한다. 예를 들어 PK/FK가 미확정이면 키를 만들어 확정 표시하지 않는다. 단순 컬럼 대응만으로 중복 제거·고객 통합 같은 엔터티 통합 규칙을 정의했다고 간주하지 않는다. Mapping 유형과 파이프라인의 실행 방식도 별도 항목으로 관리한다.

입력 대상마다 결과 또는 명시적인 보류·실패 기록이 있어야 한다. 복수 컬럼을 하나의 개념으로 통합한 결과는 관련 원천을 모두 참조하고, 미처리 대상을 집계에서 빠뜨리지 않는다. 응답 건수는 입력 대상 수·결과 수·보류/실패 수의 관계를 설명할 수 있어야 한다.

3.3 누락·건수·오류 표현

필수 필드는 생략하지 않는다. 값이 미확인·미제공·미발생이면 null과 상태·사유로 설명한다. 선택 필드의 생략은 이번 유형·응답에 포함하지 않았다는 뜻이며, 0·없음·정상·N/A로 추정하지 않는다. 빈 배열은 확인된 항목이 0개임을 뜻한다. 적용 대상이 아닌 것(not_applicable)과 필요한 근거가 없는 것(missing)도 구분한다.

counts는 입력 대상 수, 추천 결과 수, 처리된/실패한 대상 수를 분리하고, by_disposition에는 실제 판정 코드를 그대로 사용한다. 하나의 대상에 여러 추천이 있거나 복수 대상이 통합되는 경우 대상 수와 추천 수를 같게 만들지 않는다. 처리 대상 참조로 누락·중복을 확인한다.

기술 실패는 추천 disposition에 섞지 않고 failures에 대상·단계·code·message·재시도 가능 여부를 기록한다. 정상 생성 후 근거가 부족한 hold는 추천 결과로 남긴다. 실패 항목은 승인 가능 추천으로 노출하지 않는다. 실행 전체가 끝났더라도 실패가 있으면 부분 성공 등으로 표시한다. 구체적인 상태 코드 집합은 공통 정의 확정 때 맞춘다.

warnings·missing_requirements·failures의 code는 분류·집계용이고 message는 표시용이다. 코드 값은 예시를 최종 표준으로 고정하지 않고 공통 오류·상태 정의와 정합시킨다.

선택 가능 자산과 실제 사용한 자산을 구분한다. 요청의 reference_assets는 제공된 후보 목록이고, 실행 versions에는 실제 사용한 자산만 기록한다. reference_asset_usage에서 제공 자산별 사용·미사용과 사유를 남긴다. 공공 참조사전이 제공되었어도 미조회라면 public_reference=not_checked를 표시하며, 사전 부합 검증이나 신규성 확인을 완료한 것으로 표현하지 않는다.

3.4 Evidence 규칙

Evidence는 생성된 설명문만이 아니라 검토자가 확인할 수 있는 자산·위치·버전·관측 사실을 갖는다. 최소한 evidence_id, 근거 종류, 자산 참조와 버전, 범위, 해당 위치, 추천과의 연결 이유를 기록한다. 프로파일링을 사용하면 배치·실행·관측 범위가 필요하고, 사전을 사용하면 사전 항목 ID와 판본이 필요하다.

확인된 사실과 AI 해석을 구분한다. 예를 들어 ‘코드표에서 A는 예약 완료를 뜻함’은 확인 사실이고, ‘다른 회사의 접수 완료와 동일함’은 추가 검증이 필요한 판단이다. 이름이 같거나 임베딩 점수가 높다는 이유만으로 업무 의미·단위·집계 수준이 다른 항목을 통합하지 않는다.

원천값·자유서술·오류 샘플·중복 키·값 분포에도 개인정보가 들어갈 수 있다. 필요한 근거는 접근 통제된 참조나 보호된 요약으로 연결한다. 화면에 원본을 가린다는 사실만으로 프롬프트·검색 인덱스·로그가 보호되었다고 간주하지 않는다. 원천 데이터에 적힌 명령문은 데이터로 취급하며 모델 지시나 도구 실행 권한으로 사용하지 않는다.

3.5 Confidence 규칙

Confidence는 추천에 대한 근거 기반 지표이며, 검증된 성공확률이나 사람의 승인 여부가 아니다. 후보 검색 유사도, 추천 점수, 데이터 품질 지표, 독립 평가 정확도도 서로 구분한다.

기존 Mapping 기준의 평가 요소·가중치·등급 경계는 해당 기준을 명시적으로 선택한 경우만 사용한다. 표준단어·도메인·Target 설계에 자동으로 확대하지 않는다. 새 유형의 가중치·통과 점수는 07.8.1에서 정의할 정책을 참조한다. 업무 의미 모순이나 안전하지 않은 변환 같은 필수 검사 실패는 높은 점수로 상쇄하지 않는다.

화면에 점수 구성 막대나 높음·보통·낮음을 표시하려면 실제 산출 근거와 승인된 표시 정책이 있어야 한다. 아직 계산하지 않은 구성 요소를 임의의 비율로 채우지 않는다.

4. 검토·승인과 버전 연결

4.1 AI 추천과 최종 결정을 분리

AI 추천 원본을 보존하고, 검토자가 수정한 최종 결과를 별도 revision과 결정 기록으로 연결한다. 결정 기록에는 대상 추천·버전, 결정 종류, 검토자 식별정보, 시각, 수정 내용, 사유, 참조 버전을 둔다. 승인권한은 인증된 역할로 검증하며, 요청 본문의 검토자 이름만 믿고 승인하지 않는다.

승인·수정승인·반려는 기존 검토 의미를 유지할 수 있고, 검토대기·보류·이전 버전의 무효화도 표현할 수 있어야 한다. 반려·수정·보류에는 사유를 남긴다. 검토 권한의 실제 역할 배정은 공동 합의 사항이다.

승인과 실제 적용 여부는 다르다. ‘이 컬럼은 이관하지 않는다’는 판단을 승인할 수 있다. 따라서 review_status와 migration_apply를 분리하며, migration_apply는 사람의 최종 결정 전용으로 정의한다. AI의 제안은 ai_migration_apply·ai_exclude_reason으로 따로 보존한다. 사람은 AI 제외 제안을 적용으로 수정하거나 적용 제안을 제외로 수정할 수 있고, 수정·제외 사유를 남겨야 한다. 미승인, 제외 승인, 승인 후 의존성 변경 결과를 Gold 입력으로 잘못 전달하지 않는다.

일괄 승인은 사람이 실행하는 검토 동작이다. 각 추천의 버전·권한·근거·필수 검사·의존성 상태를 항목별로 확인하고, 후보가 없거나 충돌·보류 상태인 항목은 억지로 승인하지 않는다. 일부 성공 여부와 제외 사유를 반환하고 개별 결정 이력을 보존한다. 화면의 DQ 리뷰 전 미리보기와 결정 잠금 요구도 연계한다.

Baseline이라는 단어만으로 두 의미를 혼용하지 않는다. 승인 Baseline은 후속 처리에 사용할 확정 자산 묶음이고, 평가 기준선은 개선 효과를 비교할 실험 조건이다.

신규 표준 후보를 포함한 Target 초안 생성은 가능하지만 미승인 의존성을 표시해야 한다. Target 확정에는 필요한 표준의 승인 버전이 필요하며, Mapping은 승인된 Target 버전을 참조한다. 실제 Gold 적용은 승인 Mapping과 표준·Target 버전이 호환되고 적용 대상으로 선택된 경우에만 허용한다. AI가 만든 코드나 SQL은 실행 가능한 확정 규칙으로 바로 취급하지 않는다.

표준·Target·입력 구조·변환 규칙이 바뀌면 영향을 받는 추천과 승인을 찾아 재검토 대상으로 전환한다. 과거 결과를 새 버전에 자동 부착하지 않는다. 검토 시 읽은 revision과 저장 시 현재 revision이 다르면 충돌을 반환하고, 되돌리기도 새 결정 이력으로 남긴다.

4.3 모델과 재현성

모델을 쓴 실행은 공급자·모델/배포 식별자·확인 가능한 모델 버전, 프롬프트 버전, 생성 설정, 검색 자산과 실행 코드 버전을 기록한다. 공급자가 정확한 내부 모델 버전을 공개하지 않으면 확인 가능한 범위와 한계를 남긴다. 규칙만 쓴 실행은 모델·프롬프트를 ‘미사용’으로 명시한다.

버전 기록은 동일 출력을 보장하지 않는다. 원본 응답과 결과 정규화 버전을 보존하고, 동일 조건의 재실행 결과를 비교할 수 있게 한다. 개인정보가 포함된 원문 응답·프롬프트는 보호 정책에 따라 제한된 저장소에서 관리하며 일반 로그에 그대로 남기지 않는다.

5. 실행·오류·평가 연계

5.1 실행 상태와 결과 상태

실행 상태와 항목별 판단을 분리한다. 실행이 정상 완료되어도 일부 컬럼은 근거 부족으로 보류될 수 있다. 반대로 저장이나 모델 호출이 실패한 항목을 ‘표준에 없음’으로 반환해서는 안 된다.

상황처리 원칙

오류에는 요청/실행 식별자, 오류 분류, 발생 단계, 대상 항목, 사용자에게 보여줄 이유, 재시도 가능 여부를 둔다. 원천값·비밀정보·내부 저장 경로를 일반 오류 메시지에 넣지 않는다. HTTP 상태·엔드포인트·이벤트 방식·동기/비동기 전송은 별도 인터페이스 합의에서 정한다.

5.2 재전송과 재실행

같은 범위·request_id와 같은 입력 스냅샷·설정의 재전송은 기존 실행을 조회하거나 이어받도록 설계한다. 같은 request_id로 다른 입력·설정을 보내면 충돌로 처리한다. 새 모델·프롬프트·정책으로 비교하려면 새 실행을 만들고 이전 실행과의 관계를 남긴다. 실제 중복 방지 키와 보존 기간은 운영 정책으로 정한다.

결과 공개 전 참조 무결성과 건수 일치를 확인하고, 불완전한 결과를 승인 대상으로 노출하지 않는다. 중단·실패 후 복구에서도 이전 추천·결정 기록을 덮어쓰지 않는다. 보존 기간은 정해진 값으로 가정하지 않고 보안·운영 정책에 연결한다.

5.3 평가 시스템에 넘길 정보

평가에는 추천 ID·revision, 추천 유형, 원천 식별·범위·입력 스냅샷, 후보·순위·판정, 적용 사전/Target 버전, 근거·검사·Confidence 방법을 전달한다. 평가 시스템은 정답셋 버전·승인 대안·판정 기준을 별도로 붙인다. 평가용 정답과 채점 결과를 추천 필수 입력으로 넣지 않는다. 논리 원천명과 기존 평가 시스템의 키 표현이 다르면, 02.3.3에서 확인한 명시적 대응을 통해 연결한다. 저장 테이블명이나 파일명으로 원래 테이블을 임의 추정하지 않는다.

정확 일치, 승인된 대안에 대한 의미상 일치, 불일치, 판정 불가, 정답 범위 밖 예측을 구분한다. AI의 ‘근거 부족 보류’는 추천 상태이고, 평가의 ‘판정 불가’는 정답 또는 평가 근거 상태이므로 같은 필드로 합치지 않는다.

사전에 등록된 항목을 선택했다는 사실과 해당 원천의 업무 의미에 맞게 골랐다는 사실도 따로 판정한다. 정답이 없는 신규 후보를 자동 오답으로 세지 않으며, 보류·미측정 항목을 분모에서 숨기지 않는다. 유형별 정확도·평가 분모·가중치·허용오차·통과 기준은 07.8.1의 승인 정책에 연결한다. 이번 문서에서 성능 목표값을 새로 확정하지 않는다.

독립 성능 비교에서는 같은 입력과 적용 정책을 유지하고, 정답 작성에 쓴 승인 결과가 검색 근거로 노출되는지 확인한다. 승인 사례를 입력으로 사용하는 업무 실험과, 그 사례를 가린 신규 대응 실험은 평가 조건을 구분한다.

6.3 07.1.1 완료 판단

07.1.1은 G1의 입출력 연계규칙 정의·검토·이관 작업으로 완료 기준을 제안한다. 실제 구현·전체 통합 테스트·성능 통과를 이 정의 작업의 선행 완료 조건으로 묶지 않는다. 영역 공통 완료 문구를 바꾸는 최종 판단은 기술 검토와 승인 절차에 따른다.

  1. 추천 유형별 필수·조건부 입출력, 식별·근거·Confidence·버전·오류 의미가 정의되었다.
  2. AI·데이터·웹의 검토 의견을 반영했고, 기존 공통 ID·승인 상태와 맞출 항목을 기록했다.
  3. 현행 물리 데이터와의 대응·미확인 항목을 구분하고, 미결 항목은 담당 업무·수락·해소 조건·기한·차단 범위를 기록해 이관했다.
  4. 문서·입출력 예시의 형식과 참조 연결을 확인하고, 후속 구현·테스트에 전달할 검증 시나리오를 정리했다.
  5. 승인권자가 G1 검토에서 계약 판본과 적용 범위를 판정하고 그 결정이 기록되었다.

G1 검토에서는 R01의 공통 판정인 PASS / CONDITIONAL PASS / FAIL을 사용할 수 있다. 이는 판정 요청안이며, 이 문서는 현재 PASS나 완료 상태를 발급하지 않는다. CONDITIONAL PASS라면 조건·이관 주체·기한·미해소 시 차단 범위를 승인 기록에 남기고, WBS 완료 처리 여부도 그 결정에 따른다. 조건부 통과가 데이터 보호·미승인 실행 차단 같은 운영 조건을 면제하지는 않는다.
